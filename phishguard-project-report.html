1. Introduction

PhishGuard is a real-time phishing detection web application that analyses user-supplied URLs and email body text for known phishing indicators. The system employs a transparent, explainable rule-based scoring engine — every risk verdict is backed by human-readable explanations of exactly why a URL or email was flagged, rather than a black-box machine-learning decision.

Core motivation: Phishing remains one of the leading vectors for credential theft and malware delivery. Most detection tools either require cloud connectivity, offer no explanation for their verdicts, or demand ML infrastructure. PhishGuard is entirely self-contained and runs locally with zero external dependencies beyond standard Python libraries.

2. Objectives

  • Provide instant, explainable risk verdicts for any URL or email text without requiring an internet connection or API keys.
  • Surface the specific indicators that contributed to a risk score so non-technical users understand the threat.
  • Classify threats into three actionable tiers — Low, Medium, and High — each paired with concrete safety recommendations.
  • Demonstrate that a deterministic, rule-driven approach can cover the most common phishing patterns observed in the wild.
  • Deliver an accessible, professional-grade UI with no installation burden for the end user.

5. Detection Engine

The engine contains two independent scoring functions. Each function applies a fixed set of if-statement rules against the input string. Every fired rule appends a human-readable explanation to a warnings list and adds its weight to a running total score. The final score is compared against the maximum possible score (245 pts for both URL and email) to produce a percentage, which maps to a risk tier.

Scoring formula: risk % = (raw score / 245) × 100  ·  < 15% → Low  ·  15–35% → Medium  ·  > 35% → High

Each tier exposes a separate recommendations dictionary (URL_RECOMMENDATIONS / EMAIL_RECOMMENDATIONS) that maps directly to the verdict, ensuring users always receive tier-appropriate guidance without any extra branching logic.

7. User Interface Features

  • Header Bar — branded PhishGuard logo with a live "System Active" status indicator.
  • Dashboard Stats — four KPI cards (Total Scans, Threats Detected, High-Risk Threats, Safe Results) derived from session_state on every rerun; seeded with 248 demo records to demonstrate scale.
  • Scanner Selector — two buttons switch between URL Scanner and Email Scanner modes; the active scanner is persisted in session_state.
  • URL Scanner — auto-prepends https:// if the user omits a scheme; shows a structured breakdown table (Scheme, Domain, Path, Query, Length) alongside the result panel.
  • Email Scanner — accepts multi-line paste of subject + body; shows word count, URL count, email address count, and character count in a breakdown table.
  • Result Panel — circular SVG arc risk meter (0–100 normalised score), colour-coded alert banner, per-indicator severity pills (HIGH / MED), breakdown table, and safety recommendations.
  • Sample Data Table — 20 pre-scored records rendered via st.dataframe with custom column config; accompanied by a Plotly bar chart showing risk distribution.
  • Dark Theme — fully custom CSS injected via st.markdown; midnight-blue palette with Inter font.

9. Key Design Decisions

Rule-based over ML

A deliberate choice was made to use explicit if-statement rules instead of a trained classifier. This keeps the system fully auditable — every verdict can be traced to a named rule with a defined weight — and eliminates the need for a labelled training dataset, GPU inference, or model update pipelines.

Additive weighted scoring

Rules carry individual weights (10–25 pts) reflecting empirical severity. Lighter rules (double-slash paths, URL length) rarely appear alone in real phishing; heavier rules (IP-only domains, punycode, brand-spoofing subdomains) are decisive signals. The additive model means multiple weak signals accumulate into a meaningful verdict.

No external APIs

Every detection rule operates entirely on the input string. There are no calls to WHOIS databases, VirusTotal, Google Safe Browsing, or any cloud service. This makes the application usable offline and removes rate limits and API-key management.

Session state for stats

Streamlit re-executes the entire script on every interaction. Rather than incrementing a persistent counter (which would inflate figures across reruns), dashboard stats are derived at render time from the current session_state keys (url_result, email_result), seeded with realistic baseline numbers.

10. Limitations & Future Work

Current limitations:
  • Rules target textual patterns only — zero-day phishing kits using clean URLs with deceptive page content are not detectable.
  • No URL resolution: shortened URLs (bit.ly etc.) are flagged but not followed to their destination.
  • No sender/header analysis for emails — only body text is inspected.
  • Regex rules cannot catch brand-new TLD abuse until the pattern list is updated.
Potential enhancements:
  • Integrate a URL-unshortening resolver to follow redirect chains before scoring.
  • Add WHOIS age check: domains registered in the last 30 days carry extra weight.
  • Email header parser to flag spoofed From: addresses and failed SPF/DKIM.
  • Exportable PDF report of scan results for enterprise incident response use.
  • Optional ML layer (logistic regression on TF-IDF features) as a secondary signal.

12. Conclusion

PhishGuard successfully demonstrates that a transparent, rule-driven phishing detector can be built entirely in Python using only the standard library and a lightweight UI framework. The system covers 27 distinct phishing techniques across URL and email attack vectors, classifies threats into actionable tiers, and presents its reasoning in plain language accessible to non-technical users.

The project serves as a strong foundation for further research into hybrid detection approaches, and as a practical educational tool for understanding common phishing patterns and why they are effective.
